# AGENTS.md

## Scope and purpose

This file applies to the entire repository. It is the operating contract for coding agents working on the Villas Pastura website.

Keep this file concise and durable. Put version history, setup walkthroughs, and detailed implementation notes in README.md. If a subdirectory later needs materially different rules, add a narrower AGENTS.md there.

When instructions conflict, follow this order: the user's current request, legal and security requirements, this file, then README.md and local code conventions. Do not silently weaken a business, privacy, accessibility, or security rule.

## Project in one paragraph

This is the official, mobile-first, multilingual direct-booking website for Private Pool Villas Pastura in Novalja, Pag Island. It consists of a static HTML/CSS/JavaScript client, a Cloudflare Worker, Cloudflare D1, and a server-to-server Nokumo Public API v2 integration. The browser uses only same-origin /api/v1/* endpoints. The current production design creates durable booking requests; it does not create or block reservations in Nokumo.

For every task:

## Architecture boundaries

- Static source lives at the repository root and under assets/.
- Worker source lives in worker/ and is bundled to dist/server/.
- Static output is generated into dist/client/.
- Cloudflare D1 is bound as DB. Static assets are bound as ASSETS.
- Nokumo credentials and all privileged integration logic remain server-side.
- Client code must never call api.nokumo.app directly or receive the Nokumo API key.
- API responses containing availability, quotes, checkout sessions, or personal data must remain no-store.
- Prefer the existing framework-free stack. Do not add a framework or third-party runtime component unless it is necessary, materially beneficial, and approved.

## Non-negotiable security and privacy rules

- Never read out, print, log, commit, paste into source, or return secret values.
- Secrets belong in .dev.vars locally and Cloudflare secrets remotely. Keep .dev.vars.example value-free.
- Required secrets include NOKUMO_API_KEY, QUOTE_SIGNING_SECRET, and TURNSTILE_SECRET_KEY. Treat email credentials and future payment credentials the same way.
- Prices, selected units, policies, and availability from the browser are untrusted. Revalidate and reconstruct them server-side from signed or stored state.
- Validate request origin, method, body size, types, ranges, identifiers, and allowed cultures on the server.
- Keep checkout URLs opaque. Never put guest names, email addresses, phone numbers, prices, or consent data in URLs.
- Preserve idempotency for booking-request submission. A retry must not create duplicate requests.
- Do not log guest PII, tokens, secrets, full upstream payloads, or payment data.
- Store only data required for the booking request and documented operations. Retention and deletion behavior require legal approval before launch.
- No optional analytics, marketing, or functional tracking may run before the matching consent. Necessary storage may not be disabled.
- Required privacy and booking-terms consents are separate from optional marketing consent and must remain versioned and timestamped.
- Never claim that dates are held or a reservation is confirmed unless Nokumo has actually accepted the corresponding reservation state.
- Do not implement CreateReservation or any other Nokumo write operation unless the user explicitly requests it and the payload mapping, status rules, idempotency, failure recovery, and legal copy have been approved.
- Do not add real card handling to this application without a separately approved PCI-safe IPG design. Nokumo is not the card processor.

## Booking-domain invariants

### Property and inventory

- Nokumo property ID: 25532.
- Allowed accommodation-unit-type IDs: 8481 and 8482.
- Nokumo models Pastura as one property containing two identical accommodation unit types, each with one unit.
- Guest-facing UX treats them as one product. Do not ask the guest to choose a concrete villa.
- A stay is available only when one same villa/unit type can fulfil the entire date range. Never combine partial availability from both villas.
- Equivalent offers from both villas are deduplicated. When both can fulfil the same offer, prefer the candidate with the lower accommodation-unit-type ID. Do not add round-robin allocation.
- Calendar availability is guidance. The authoritative decision is the complete-stay booking-engine offer search immediately before an offer is shown and again before submission.
- Unknown or missing dates are unavailable; do not infer availability.
- Availability is live/on-demand. Cache only non-critical metadata or content when staleness cannot create an invalid booking decision.

### Guests and stay

- Maximum occupancy is eight guests.
- Current guest bands are adults 18+, children 0–11, and young guests 12–17.
- Do not collect exact child ages unless Nokumo pricing or a verified legal rule cannot be satisfied from the bands. The current integration sends representative ages only for server-side pricing.
- Stay and guest validation must exist on both client and server, with the server authoritative.
- Keep date, guest, consent, payment-preference, and personal-detail state when the guest moves backward to make a correction, unless clearing it is necessary for safety.

### Offers, prices, services, and policies

- Nokumo may return multiple rate plans, special offers, prices, restrictions, cancellation policies, prepayment policies, mandatory services, and optional services. Never assume a single rate.
- Preserve distinct offers when their rate plan, price, policy, restriction, or included services differ.
- Accommodation price is separate from mandatory charges.
- Mandatory charges such as cleaning and tourist tax are shown transparently in the price breakdown.
- Included services and direct-booking perks are visually prominent but must not be misrepresented as separate paid items.
- Use stable Nokumo IDs for property-specific display overrides. Do not match business logic by mutable English names.
- Guest-facing overrides and local display-only perks belong in config/booking-presentation.json and must conform to its JSON Schema.
- Local display-only perks use a local: ID and must never be sent to Nokumo as add-on services.
- Unknown Nokumo IDs fall back safely to upstream labels and data.
- All totals and policies shown at checkout must come from a fresh server-side calculation. Do not calculate authoritative prices in browser JavaScript.

### Payment and reservation status

- Current payment preferences are pay by link using 3-D Secure and bank transfer. In both cases, the agency sends payment instructions after reviewing the request.
- The current flow stores a booking request in D1 and prepares internal and guest notifications. Email failure must not lose the request.
- A stored booking request is not a hold and not a confirmation.
- Known future mapping, only when CreateReservation is approved: bank transfer uses statusId 1 (hold); a successfully completed card flow uses statusId 2 (confirmed); the distribution channel is the fixed website-direct channel.
- Bank transfer must not invoke Monri, WSPay, or another card IPG.
- If email delivery is not configured, show an honest pending-delivery state and keep the D1 record actionable.

## Content, localization, and presentation

- Supported languages are EN, DE, HR, and IT.
- Any guest-visible content change must be applied coherently in all four languages, including validation messages, accessibility labels, metadata, and structured data where applicable.
- Do not invent ratings, reviews, distances, policies, facilities, or local recommendations. Reviews must be authentic and approved.
- This must read as the official property website written with owner and local host knowledge, not as generic AI-generated feature copy.
- Prefer concrete, verifiable language and local insight. Avoid filler, repeated claims, and keyword stuffing.
- The two villas are adjacent, but each is fully private: each has its own entrance, fenced terrace, and private heated pool; no outdoor facilities are shared.
- Use “heated pool” wherever a pool amenity is described. Titles and short brand headlines may use “private pool” when that is clearer.
- Keep the direct-booking value proposition visible: best direct-booking terms, priority support from a local hospitality team with more than 15 years of experience, and the approved rate perks.
- Approved contact phone: +385 95 7328 532.
- Property-specific rate label: Exclusive Direct Booking Offer.
- Property-specific perks currently include free early check-in, free late check-out subject to availability, free parking, pets without surcharge, and free 22 kW EV charging. Keep display overrides configurable rather than hardcoded in rendering code.
- FAQ content should cover booking and price, villa and pool, arrival and location, and local host advice. Visible FAQ content and FAQPage JSON-LD must be generated from the same approved source.

## UX and CRO rules

- Design mobile-first while preserving the established desktop composition.
- Avoid crowded mobile above-the-fold layouts, duplicate instructions, duplicate headings, and repeated explanations of live checking.
- On mobile, progressively disclose guest controls and the final availability action after dates are selected.
- Date selection uses one clear instruction and explicit confirmation. Closing with X, Escape, or backdrop discards unconfirmed changes.
- Calendar months use a fixed six-week grid to prevent layout shift. Unavailable dates are clearly disabled or crossed out; do not add a redundant or inaccurate legend.
- Guest counts use accessible minus/plus steppers. Do not open the mobile keyboard for these controls.
- Do not introduce nested scrolling in the gallery, lightbox, modal, or checkout flow.
- Center icons within their hit areas. Previous, next, close, menu, and language controls must look finished at all supported widths.
- Preserve visible focus, keyboard operation, Escape handling, focus trapping in dialogs, touch/swipe behavior where already supported, and reduced-motion preferences.
- Interactive targets should be at least 44 by 44 CSS pixels.
- Meet WCAG 2.2 AA contrast and interaction requirements. Do not rely on color alone for availability, errors, or selection.
- Use accurate action labels: “Send booking request” for the current final submit, not “Book now” or wording that implies confirmation.

## Performance and dependency standards

Treat these as launch budgets and regression guards, measured on a production-like build:

- Mobile Lighthouse/PageSpeed Performance: at least 90.
- Accessibility, Best Practices, and SEO: at least 95 each.
- Core Web Vitals at the 75th percentile: LCP at most 2.5 s, INP at most 200 ms, CLS at most 0.1.
- A change should not reduce any Lighthouse category by more than five points without an explicit, documented trade-off.

Implementation rules:

- Keep JavaScript and CSS small and dependency-light.
- Use semantic HTML first; use JavaScript only for behavior that requires it.
- Give images explicit dimensions or aspect ratios to prevent CLS.
- Keep responsive art direction for mobile and desktop. Never upscale or create an accidental compositional crop.
- Lazy-load below-the-fold images, but do not lazy-load the LCP image.
- Generate optimized WebP/AVIF derivatives where supported, strip EXIF/GPS, and preserve sRGB.
- Do not add third-party scripts, fonts, widgets, trackers, booking components, or tag managers unless necessary and approved.
- If a performance target cannot be measured in the current environment, state that clearly; do not claim a score without a recorded run.

## SEO, structured data, and AI-search rules

- Keep page titles, descriptions, canonical URLs, headings, image alt text, and entity names accurate and non-duplicative.
- Maintain a consistent entity: Private Pool Villas Pastura, Novalja, Pag Island, official direct-booking website.
- Structured data must match visible content exactly. Never expose placeholder, stale, hidden, or invented claims in JSON-LD.
- FAQPage, ImageGallery, review, lodging/vacation-rental, breadcrumb, and organization data should be used only where valid for the visible page.
- Any new editor-managed JSON content or configuration must include schemaVersion, stable IDs, validation, and a JSON Schema when the structure is non-trivial.
- Generate visible content and related JSON-LD from one source whenever possible.
- Legal and placeholder pages remain noindex until their content is complete and approved.
- Preserve human-readable local expertise; AI-search optimization is achieved through clear entities, factual answers, consistent data, and crawlable semantic markup, not keyword repetition.

## Database and operational rules

- D1 migrations are forward-only. Never edit an already-applied migration; add the next numbered migration.
- Do not delete, rewrite, or inspect production booking data without explicit authorization.
- Schema changes must preserve existing checkout sessions, booking requests, idempotency keys, consent evidence, and email-status recovery.
- Production configuration, secrets, DNS, email bindings, Turnstile, WAF/rate limits, and remote migrations require explicit authorization and a documented rollback or recovery path.
- The development API key shared during prototyping must be rotated before production launch.

## Required verification

Run npm run check before handing off any code change. Add focused tests for changed business logic.

For booking changes, verify at minimum:

- calendar guidance and authoritative full-stay search;
- both unit types, same-villa continuity, offer deduplication, and lower-ID preference;
- multiple rates and policies;
- adults and both child bands up to total capacity eight;
- checkout-session creation, refresh, expiry, browser Back/BFCache, and change-dates-or-guests flow;
- duplicate-submit protection and email pending/failure states;
- no CreateReservation call;
- no secret or PII exposure.

For UI changes, manually check at least:

- a representative 440 x 956 mobile viewport;
- desktop around 1440–1920 px wide;
- keyboard-only operation and visible focus;
- EN, DE, HR, and IT;
- no console errors, layout shifts, nested scrollbars, clipped controls, or broken links.

For content/configuration changes, validate JSON, JSON Schema, generated artifacts, structured data, translations, links, and fallback behavior.

## Definition of done

A change is done only when:

- the requested behavior is implemented without unrelated redesign;
- security, booking-domain, privacy, accessibility, and localization invariants still hold;
- generated output is rebuilt when its source changes;
- npm run check passes;
- relevant manual flows are verified;
- changed files, tests run, environment limitations, and remaining risks are reported clearly;
- README.md and this file are updated only when the change alters durable project behavior or agent instructions.
